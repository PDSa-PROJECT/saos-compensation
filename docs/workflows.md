# Local judgment pipelines

`saos_workflows.pipelines` contains three independent ZenML pipelines: `collect_cases`, `find_targets` and `extract_features`. Each module owns its step and stage-specific helper functions; there is no separate operations layer. Workflow helpers belong in `common` only when their logic is reused across pipelines; no such module is currently needed. Shared dataset logic stays in `saos_dataset`, including the row schema, validation and serialization in `storage.parquet` through `read_rows` and `write_rows`. Each pipeline accepts explicit local Parquet paths; run them separately to review and choose the input to the next stage. There is no workflow CLI or duplicated acquisition/model settings. The existing `get-raw-data` and `process-data` commands, files and checkpoints remain unchanged.

- `collect_cases(start_date, end_date, phrases, output_path, selected_phrases=None, max_records=0, timeout=30.0)` searches SAOS with one shared timed session, fetches unique full judgments up to a positive cap (0 means unlimited), joins court metadata and retains selected, filtered and rejected IDs. It does not run a model.
- `find_targets(input_path, output_path, config_dir=None)` runs the existing embedding-based amount logic on selected cases only. It stores the target handoff separately; unconfirmed amounts remain null. It does not load Basal.
- `extract_features(input_path, output_path, config_dir=None)` consumes that handoff without rerunning target matching, applies the existing Basal predictor and admission rules, and retains rejected/skipped rows. It loads a local model and locality metadata only when the selected cases require them.

Each run creates one new plain Parquet file via `saos_dataset.storage.parquet`. The output path must not exist, and later stages require an explicitly chosen prior file. The small shared row layout carries complete source-detail JSON, normalized text, selection status/reason, exact decimal PLN target, target context, feature evidence/reviews and final eligibility. Target/feature details are JSON columns; no extra legacy case files are created.

Relative input/output paths, `config_dir` and `.env` use the process working directory. No pipeline discovers a repository root from its source location. Processing configuration supplies `config["paths"]` from runtime settings `MODEL_CACHE_PATH`, `ENCODER_CACHE_PATH` and `LOCALITIES_PATH` (defaults: `basal_weights`, `embedding_weights`, `tmp/gugik`). The target stage uses the configured encoder cache; the feature stage passes the configured Basal and locality paths to the shared loaders. Use absolute paths when launching from another directory to keep locations stable.

Both workflows use `saos_dataset` for query construction (`acquisition.settings.search_query`), pagination continuation (`clients.api.has_next_page`), admission/reason composition (`extraction.quality.admission_decision`), locality initialization (`processing.localities.load_locality_context`) and model/worker lifetime (`clients.basal.open_server`). Admission distinguishes retention from validity: debug attempts can receive metadata while remaining ineligible, and missing damage still prevents legacy retention. Combined rejection reasons use the legacy “text feature extraction skipped” wording when predictors were not evaluated. Existing source, target, predictor, metadata and device checks remain shared. Legacy processing keeps page/output durability, pending state, checkpoints and locality-hash verification; the individual pipeline modules keep phrase union, record caps, stage skipping and Parquet mapping. The target-only stage continues to call the existing amount extractor, and the feature stage calls only the target-prepared predictor helper.

ZenML tracks run metadata and output *path strings*, **not the Parquet file as a portable ZenML artifact**. Keep those paths accessible on the Mac and preserve their files separately. There is no successful-output cache, automatic resume, S3 access or remote inference; an interrupted run starts over and can reuse its chosen output path only if no file was published. No live SAOS collection or real Basal/MiniLM inference was verified here: the three decorated pipelines were exercised with fake services and model responses in an isolated local ZenML repository. Before running real extraction, sync the locked dependencies and ensure model caches/devices and locality data are available. Local tracking setup is documented [here](../infrastructure/zenml/local/README.md); shared hosting remains [deferred](../infrastructure/zenml/shared/README.md).
